# Case study — LLM inference performance engineering on an 8×H200 node

*Solo project executed end-to-end (design, measurement, analysis, write-ups) at the author's company — phase 1 of `nanoserve-mini`, a 12-week LLM inference performance lab. Delivered in 3 weeks around a production machine: GPU access was limited to three time-boxed server sessions, so all tooling, configs and session plans were prepared and rehearsed on development hardware in advance, and each session was optimized for maximum use of the hardware time. The performance-research methodology built here was subsequently codified and adopted as the basis for GPU compute-server performance studies across the organization. Every number below traces to committed benchmark artifacts and git-tracked session plans: [github.com/Czyszka/nanoserve-mini](https://github.com/Czyszka/nanoserve-mini).*

**Scope & stack.** Stood up and characterized a multi-model serving baseline on a dual-socket 8× NVIDIA H200 NVL node (PCIe Gen5 interconnect only — no NVLink/NVSwitch), then answered a live procurement question: would NVLink 4-way bridges pay off? Stack: vLLM v0.20 (Docker Compose), LiteLLM gateway, Prometheus + Grafana + DCGM telemetry, torch profiler, `vllm bench serve`. Primary workload: Kimi-K2.6 — an open-weight 1T-parameter MoE (~554 GB weights, 61 layers, TP=8, EAGLE3 speculative decoding; 80.2% SWE-bench Verified) — co-resident with DeepSeek-V4-Flash (FP8); Qwen3.6-35B-A3B as a single-GPU control model.

**Capacity planning from first principles.** The initial DP+EP bring-up of the 1T model crashed at startup; the root cause was reconstructed from engine logs alone via vLLM's memory accounting: dense/attention weights replicated per-rank pushed the footprint to 88.44 GiB/GPU against an 84.24 GiB budget — leaving −19.08 GiB for KV cache. Re-sharding as TP=8 (69.3 GiB/GPU) recovered the deficit. The same accounting sized the co-tenant's memory cap by a bounded sweep: 0.15 fails (−0.49 GiB KV), 0.20 adopted, 0.25 rejected — it buys concurrency a single-stream phase cannot use, at the cost of the latency-critical tenant's headroom.

**Metric definitions treated as engineering objects.** TTFT proved ill-defined for reasoning models — the reasoning channel streams ~2.8× earlier than final-answer content (0.209 s vs 0.592 s) — so the client metric was split into two channels (any-token vs content). The same instrumentation caught the gateway silently dropping the reasoning stream (direct: 26 chunks / 242 reasoning chars; proxied: 3 / 0) and priced gateway overhead at +17–26 ms median TTFT. An EAGLE3 A/B test rejected the naive single-shot readout (3.8× — an output-length artifact) in favor of repeated-run medians: 2.0× TTFT p50 (837 vs 1,675 ms) and 1.9× decode throughput (111.6 vs 58.7 tok/s), for 0.76 GiB/GPU of draft weights.

**Root-causing a bottleneck the headline metric hides.** Under load, `nvidia-smi` reported 100% GPU-Util while nothing was saturated (DCGM: DRAM_ACTIVE 7–9%, SM_ACTIVE ~20%, PCIe at ~10% of nominal, ~30% of power limit) — occupancy, not utilization. The decode step was modeled as `T(step) = F_host + N_rounds · r(link, ranks) + W_silicon` and the competing hypotheses were separated by single-variable interventions, with verdict criteria pre-registered in session plans before any data was collected:

- **TP curve** on the control model (TP=1→8, all else fixed): batched throughput 1,202 → 1,404 → 680 → 257 tok/s; scaling efficiency 100% → 58% → 14% → 2.7%.
- **Falsification probes:** `NCCL_P2P_DISABLE` → null effect; cross-socket GPU placement → null (UPI exonerated) ⇒ the cost scales with all-reduce participant count and synchronization, not per-hop link quality.
- **Host-floor decomposition** at TP=1: speculative-decoding orchestration = 40% of the step; disabling CUDA Graphs exposes +46.2 ms/step of kernel-launch overhead; CPU frequency governor → null.
- **Profiler traces:** single-stream is floor-bound (63% host gaps, 22.5% NCCL); batched TP8 is transport-bound (83.9% NCCL, PCIe RX pinned at 7.2–7.9 GB/s/GPU). Two independent methods converge: 53.3% NCCL share in the TP4 profile vs ~52% implied by client-side throughput deltas.

**A hardware decision quantified before spending.** The measured communication shares fed an Amdahl model with a topology-aware capture factor (ring all-reduce across two 4-GPU islands ⇒ 6/8 segments captured; 128 vs 900 GB/s bandwidth ratio): projected NVLink gain ≈1.0× (TP≤2), 1.15× (TP4 interactive), ~1.8–2.1× (TP4 batched), ~2.2–2.7× (TP8 batched; ideal-link ceiling 6.2×). Delivered as a workload-conditional GO/NO-GO table that composes with any bridge price — together with the free software levers to exhaust first: a c=16 scheduler pathology worth ~4× by operating point alone, and the 40% spec-decode share of the host floor.

**Demonstrated:** GPU performance engineering (NCCL collectives, PCIe/NUMA topology, CUDA Graphs, DCGM, torch profiler) · distributed inference (TP/DP/EP trade-offs, MoE serving, speculative decoding, KV-cache budgeting) · vLLM internals and production-style serving (Docker Compose, gateway routing, Prometheus/Grafana) · experimental method (pre-registered criteria, dose–response interventions, cross-method validation, explicit noise bands) · decision-grade technical writing.
